TARGET UPFRAME SYSTEM — PROJECT SUMMARY

1. GOAL

Build a production-grade video upframing pipeline that takes a normal broadcast video, primarily 25 fps football/soccer footage, and produces a 50 fps version with AI-generated intermediate frames.

The intended user experience is deliberately simple:

    upframe input.mp4 output_50fps.mp4

The system should handle the entire process automatically: inspect the input, decode it, interpolate the missing frames, use multiple GPUs efficiently, encode the result, preserve audio/sync, and report what happened.

This is not a research/training project. The system should use existing pretrained VFI models/repositories as plug-and-play components.


2. TARGET INPUT

The primary target is professional/online football broadcast footage such as:

- 1920×1080
- ~25 fps
- H.264
- yuv420p / BT.709
- AAC audio
- ~13 Mbps video bitrate
- Long-form content such as 60–120 minute matches

The supplied sample videos are representative of the target workload:

- output_test.mp4
- output_test(1).mp4
- output_test_2.mp4

They contain typical football-broadcast characteristics:

- Wide tactical camera shots
- Fast camera pans/tracking
- Multiple players moving independently
- Small, fast-moving football
- Player-player occlusion
- Legs, feet and arms moving rapidly
- Pitch markings and strong geometric lines
- Goal nets
- Grass texture
- Crowds
- LED advertising boards
- Scoreboards/TV graphics
- Persistent TV watermark/logo
- Compressed broadcast/streaming imagery

These characteristics make the footage substantially harder than a simple synthetic interpolation benchmark.


3. WHAT THE AI SHOULD ACTUALLY DO

For every pair of consecutive source frames:

    Frame N          Frame N+1
       |                 |
       +------ VFI ------+
                |
         Frame N+0.5

So:

25 fps source

    A ----- B ----- C ----- D
         ^       ^       ^
         generated intermediate frames

50 fps output

    A -- A.5 -- B -- B.5 -- C -- C.5 -- D

The system should generate one intermediate frame per source-frame interval.

There is no need for recursive 25→50→100→50 processing.


4. QUALITY TARGET

The main objective is broadcast-safe temporal interpolation, not merely maximizing an academic VFI metric.

The generated frames should look natural at 50 fps without introducing obvious:

- Player deformation
- Duplicate limbs
- Ghost players
- Ball artifacts
- Broken feet
- Warped pitch lines
- Distorted goal nets
- Flickering advertisements
- Unstable scoreboard graphics
- Temporal shimmer
- Texture crawling
- Camera-motion artifacts

In particular, the system needs to preserve the identity and geometry of:

Players:
Correct bodies, limbs, feet, jerseys and player positions.

Ball:
The ball is small but extremely important. Incorrect interpolation can create ghost balls, missing balls, or an incorrect trajectory.

Pitch geometry:
Lines such as touchlines, penalty boxes and the center circle are excellent indicators of interpolation errors because they should remain geometrically coherent.

Broadcast graphics:
Scoreboards, logos and watermarks should remain stable rather than being warped between frames.


5. MODEL STRATEGY

The system should be model-agnostic.

Initial candidates:

RIFE / Practical-RIFE:
Primary production-speed baseline.
- Mature ecosystem
- Fast
- Relatively efficient
- Good 2× interpolation
- Appropriate for large-scale processing

AMT:
Primary quality-oriented candidate.
It should be benchmarked against RIFE specifically on difficult football motion.

FILM:
High-quality reference candidate, particularly useful for assessing difficult/large motion, although computational cost is higher.

IFRNet:
Potential efficiency alternative.

Important design principle:

                    +-- RIFE
                    |
Input -> Pipeline --+-- AMT
                    |
                    +-- FILM
                    |
                    +-- IFRNet

The processing system should not be tightly coupled to one VFI implementation. A model can be swapped without rewriting the video-processing pipeline.


6. NO TRAINING OR FINE-TUNING

This is a strict requirement.

The system should use existing pretrained models, repositories and weights.

There is no requirement to:
- collect football datasets
- train a model
- fine-tune a model
- develop a new neural network
- build a football-specific model

The engineering work is primarily around productionizing existing VFI models.


7. HARDWARE

Target machine:

    GPU 0 -> NVIDIA L40S 48 GB
    GPU 1 -> NVIDIA L40S 48 GB
    GPU 2 -> NVIDIA L40S 48 GB

Preferred architecture: three independent GPU workers, rather than splitting one model across three GPUs.

                    Input video
                        |
                 Frame/chunk scheduler
                   /       |                         /        |                     GPU 0       GPU 1     GPU 2
             Worker      Worker    Worker
                \          |         /
                 \         |        /
                    Ordered merge
                         |
                       Encoder
                         |
                  output_50fps.mp4

Each GPU independently processes chunks of the video.


8. PERFORMANCE REQUIREMENT

Desired processing time:

1.0–1.3× the duration of the source video.

Examples:

Input       Desired processing time
20 min      ~20–26 min
60 min      ~60–78 min
90 min      ~90–117 min
120 min     ~120–156 min

This is not strict live real-time.

For a 90-minute 25-fps match:

    135,000 source frames
    ~135,000 intermediate frames to generate

To finish in 90–117 minutes, the three GPUs collectively need roughly:

    ~19–25 interpolations/sec

or approximately:

    ~6–8.5 interpolations/sec/GPU

This is why the L40S hardware makes heavier models worth benchmarking rather than automatically choosing the fastest model.

10. SCENE-CUT HANDLING

The system should not blindly interpolate every pair of frames.

Normal play:

    Frame A -> Frame B
             |
            VFI
             |
       Intermediate frame

Hard cut:

    End of camera shot
            |
           CUT
            |
    Different camera/replay

The system should not produce a synthetic frame combining the two shots.

Otherwise the result can look like a wide field shot and a close-up camera being blended into an impossible hybrid frame.

Therefore the pipeline needs basic scene/shot-cut detection and should bypass interpolation across hard cuts.


11. TIMESTAMP / FPS HANDLING

The input videos are nominally 25 fps but the samples report slightly different container timing, around 25.02 fps.

Therefore the system should not simply assume every frame is exactly 40 ms apart without checking timestamps.

The pipeline should inspect:

- PTS
- duration
- frame count
- nominal FPS
- actual frame timing
- audio timing

Then generate intermediate timestamps appropriately.

Goal:

50 temporal samples per second while maintaining A/V synchronization.

If exact 50.000 fps output is required, the pipeline can normalize/resample timing explicitly rather than accidentally introducing drift.


12. AUDIO

Audio does not need AI processing.

Preferred architecture:

Video:
25 fps -> VFI -> 50 fps -> encode

Audio:
original AAC ----------------> copy

The output should retain the original audio whenever possible rather than unnecessarily re-encoding it.


13. RESOLUTION

The source is already good-quality 1080p broadcast material.

Do not automatically add super-resolution.

The goal is temporal upframing, not spatial enhancement.

Adding an unnecessary SR/restoration model could introduce:
- hallucinated details
- altered player appearance
- artificial grass
- changed text/logos
- unwanted sharpening

Default behavior:

    1920×1080 @ ~25 fps
            |
           VFI
            |
    1920×1080 @ 50 fps

Not:

    1080p -> AI restoration -> 4K -> VFI


14. CHUNKING

Long matches should be divided into manageable chunks:

    Match
    |
    +-- Chunk 0
    +-- Chunk 1
    +-- Chunk 2
    +-- ...
    +-- Chunk N

Chunks should have a small frame overlap at their boundaries.

Example:

    Chunk A: frames 0–1001
    Chunk B: frames 1000–2001

This ensures the worker has the neighboring frame required for interpolation.

The merge stage removes duplicate overlap output and restores correct global ordering.


15. CRASH RECOVERY

Because target videos may be 1–2 hours long, the system should not lose an entire job because one GPU process fails.

A production-oriented implementation should track:

- chunk ID
- source frame range
- GPU
- status
- processing time
- output location
- checksum/validation

Example:

    chunks 0–36 -> complete
    chunk 37    -> failed
    chunks 38+  -> possibly complete

The scheduler should be able to retry the failed chunk rather than restarting the whole match.


16. USER EXPERIENCE

Simplest interface:

    upframe input.mp4 output.mp4

Advanced interface:

    upframe       --input match.mp4       --output match_50fps.mp4       --model rife       --gpus 0,1,2

Potential future configuration:

    upframe       --input match.mp4       --output match_50fps.mp4       --model auto       --gpus 0,1,2       --quality broadcast

The user should not need to know anything about VFI internals.


17. SUGGESTED SOFTWARE ARCHITECTURE

A clean repository could look like:

    upframe/
    |
    +-- cli/
    |   +-- upframe.py
    |
    +-- pipeline/
    |   +-- probe.py
    |   +-- decode.py
    |   +-- scene_detect.py
    |   +-- scheduler.py
    |   +-- timestamps.py
    |   +-- merge.py
    |   +-- encode.py
    |   +-- qc.py
    |
    +-- models/
    |   +-- base.py
    |   +-- rife.py
    |   +-- amt.py
    |   +-- film.py
    |   +-- ifrnet.py
    |
    +-- workers/
    |   +-- gpu_worker.py
    |
    +-- configs/
    |   +-- football_25_to_50.yaml

Important abstraction:

    class VFIModel:
        load()
        interpolate(frame_a, frame_b)
        unload()

The rest of the system should not care whether the underlying model is RIFE, AMT or FILM.


18. DOCKER / REPRODUCIBILITY

The system should ideally be packaged as a Docker image containing:

- CUDA-compatible PyTorch
- FFmpeg
- model dependencies
- pretrained model weights
- upframe wrapper
- GPU runtime configuration

Conceptually:

    Host
     |
     +-- Docker
          |
          +-- GPU 0 -> worker
          +-- GPU 1 -> worker
          +-- GPU 2 -> worker

This avoids dependency conflicts between different VFI repositories and makes deployments reproducible.


19. QUALITY CONTROL

The pipeline should automatically generate a processing report.

Example:

    UPFRAME REPORT
    --------------------------------
    Input:             match.mp4
    Output:            match_50fps.mp4

    Resolution:        1920×1080
    Input FPS:         ~25 fps
    Output FPS:        50 fps
    Duration:          91:32

    Model:             RIFE
    GPUs:              0,1,2

    Source frames:     137,xxx
    Generated frames:  137,xxx
    Scene cuts:        xx

    Processing time:   98:14
    Realtime factor:   1.07×

    Audio:             stream copied
    Encoding:          H.264
    Status:            SUCCESS

This makes it possible to benchmark different VFI models objectively.


20. WHAT SHOULD BE BENCHMARKED

The supplied football clips should become the standard regression/benchmark set.

At minimum compare:

    RIFE
    vs
    AMT
    vs
    FILM

Use the same clips and hardware.

Objective engineering metrics:
- Frames/sec
- Interpolations/sec
- GPU utilization
- VRAM usage
- Total processing time
- Realtime factor
- Encoding overhead

Visual quality:
- Ball
- Player limbs
- Player interactions
- Occlusions
- Camera pans
- Pitch lines
- Goal net
- Grass
- LED boards
- Scoreboard
- Watermark stability

The winner is not necessarily the model with the best academic benchmark score.

The winner is the model that provides the best combination of:

    football visual quality
    +
    temporal stability
    +
    throughput
    +
    operational reliability

while staying within the 1.0–1.3× processing target.


21. WHAT V1 SHOULD BE

The first useful production prototype should stay relatively simple:

                         V1
                          |
                  Existing pretrained VFI
                          |
                      RIFE first
                          |
             +------------+------------+
             |            |            |
           GPU 0        GPU 1        GPU 2
             |            |            |
             +------------+------------+
                          |
                    Ordered merge
                          |
                     FFmpeg encode
                          |
                          v
                      50 fps MP4

V1 should include:

- automatic probing
- chunking
- scene-cut protection
- timestamp preservation
- audio preservation
- multi-GPU processing
- progress reporting
- crash/retry capability
- processing report

Then benchmark AMT and FILM as drop-in alternatives.


22. EXPLICITLY OUT OF SCOPE

For this version, we are not trying to build:

- A new VFI neural network
- A training pipeline
- A fine-tuning pipeline
- A football-specific trained model
- A diffusion-based generative video system
- Automatic 4K enhancement
- Full video restoration
- Live broadcast processing
- A complex AI agent

The system is fundamentally an industrial wrapper/orchestrator around proven pretrained VFI models.


ONE-SENTENCE DEFINITION

Build a Dockerized, multi-GPU, production-oriented `upframe` pipeline that takes ~25 fps 1080p football broadcast video, uses existing pretrained VFI models to synthesize one intermediate frame between every source-frame pair, handles cuts/timestamps/chunking/audio automatically, and outputs a stable 50 fps video in roughly 1.0–1.3× the source duration on 3× L40S GPUs.
